## 一、项目介绍与个人职责

<a id="q01"></a>
### Q01：介绍一下这个项目。

**参考回答：**

> 这是一个面向代码阅读、文件修改和测试执行的 Python Coding Agent。我基于开源框架做复现和二次开发，复用了模型与工具交互、MCP、Skills、Memory 和子 Agent 等能力。
>
> 我重点改进了执行恢复、Shell 命令生命周期和结构化上下文管理，并接入本地 Qwen3-8B 做评测。它的特点是工具真正修改文件和执行测试，最后用独立测试判断任务是否完成，而不是只看模型是否说“完成了”。

**深入追问：和聊天机器人有什么区别？**

> 聊天机器人主要返回文本；这个系统会根据模型选择执行具体工具，并把真实文件和命令结果继续反馈给模型。因此还需要管理权限、副作用、超时、状态和验收。

**回答边界：** 这是轻量工程项目，不称为已经大规模生产部署的企业级平台。

<a id="q02"></a>
### Q02：哪些是你自己做的，哪些来自上游？

**参考回答：**

> 基础 Agent Loop、工具体系、MCP、Skills、Memory 和子 Agent 主体来自 claude-code-from-scratch。我参考 learn-claude-code 学习模块划分和工作流思路，但没有把两套框架完整拼接。
>
> 个人重点改动是原子会话保存、执行日志和恢复处理，Shell 增量输出与进程组清理，结构化摘要及失败回退，以及非法工具调用历史处理和固定题集评测。

**深入追问：为什么不是从零开发？**

> 复用基础框架让我能在完整系统上集中验证具体问题，而不是只实现一个演示循环。我会用代码差异、故障案例和测试说明自己的贡献，不把已有组件都算成原创。

**代码依据：** [上游差异与阅读指南](CODE-READING-GUIDE.zh-CN.md)。

<a id="q03"></a>
### Q03：项目解决了什么实际问题？

**参考回答：**

> 我关注的是长任务中“执行过什么、是否成功、还能不能继续”不清楚的问题。比如文件已经改了但进程中断，重新运行可能重复副作用；Shell 超时后可能留下子进程；历史很长时，模型可能忘记限制或把计划误当完成。
>
> 对应地，我用执行状态记录、命令生命周期管理和结构化任务摘要降低这些风险。

**深入追问：这些问题都完全解决了吗？**

> 没有。未知副作用仍需要核验，摘要不保证语义无损，某些逃离进程组的进程也不在清理保证内。我把保证范围写清楚，并保留证据用于定位问题。

<a id="q04"></a>
### Q04：整体架构怎么讲？

**参考回答：**

> 可以分成模型层、执行层和状态层。模型层选择动作；执行层管理工具、权限和命令；状态层保存消息、执行日志和记忆。CLI 把用户请求交给 Agent，Agent 请求模型、执行工具、回传结果，直到停止或达到预算。评测器在外层独立验收。

```text
用户 → Agent → 模型 → 参数与权限检查 → 工具执行
              ↑                         ↓
              └──── 工具结果与历史 ──────┘
                    快照 / 执行日志
                           ↓
                      独立测试验收
```

**深入追问：本地模型在哪里加载？**

> 模型由外部 vLLM 服务加载并常驻，Agent 通过兼容 API 请求它。Agent 对象不是模型实例，不会因为创建一个子 Agent 就加载一份模型权重。

## 二、Agent 规划与执行链路（Harness）

代码入口：[agent.py](../../python/mini_claude/agent.py)、[__main__.py](../../python/mini_claude/__main__.py)。

<a id="q05"></a>
### Q05：ReAct 在你项目里具体是什么？

**参考回答：**

> 它是模型根据当前任务和观察决定下一步工具动作，程序执行后把结果交回模型，模型再继续选择动作。比如先读源码，再编辑，接着运行测试，根据失败反馈修复。
>
> 这里不要求我们获取模型内部完整思维链，记录的是可见文本、工具调用和实际反馈。

**深入追问：与固定工作流相比有什么优缺点？**

> 它能根据新反馈调整路径，但执行过程更不确定。所以不能完全靠提示词，需要程序控制权限、预算、取消和验收。

<a id="q06"></a>
### Q06：Agent 什么时候停止？停止就算成功吗？

**参考回答：**

> 当前普通循环在模型不再发工具调用、达到预算、被取消或异常时停止。停止只是执行状态，不能代表任务成功。
>
> 工具完成、文件修改成功、任务验收通过是三个层次。比如编辑成功只说明文件变了，最终仍要通过独立测试。

**深入追问：模型说“我接下来修复”却没有工具调用怎么办？**

> 我们遇到过这种失败。后续候选增加一次性接续：识别到测试失败或零项测试，之后没有成功编辑，仍有预算但模型只输出文字时，提醒继续修复或明确报告无法继续。它属于独立实验，不是无限追问直到成功。

**回答边界：** 接续只识别有限直接测试命令，不是通用语义任务完成判定器。

<a id="q07"></a>
### Q07：Plan 模式和审批怎么实现？

**参考回答：**

> 普通 CLI 的 Plan 模式通过权限限制普通文件修改和 Shell，只允许写指定计划文件。用户审批后再切换执行模式。
>
> 它与我们后续实验中的 update_plan 不一样：前者是工作模式和权限切换，后者是维护当前任务计划并注入上下文的工具。benchmark 去掉 update_plan，没有删掉原有只读 Plan 模式。

**深入追问：能保证所有操作都只读吗？**

> 要看实际工具和权限分支，不能只看角色名称。应用层规则也不是操作系统沙箱，外部工具和 Shell 的能力必须另外审查。

<a id="q08"></a>
### Q08：只读工具并行怎么做？

**参考回答：**

> OpenAI 路径把连续的安全只读工具分组，用 asyncio.gather 调度；修改和 Shell 等其他工具按顺序执行。但部分文件处理器仍然同步运行，所以 gather 不等于所有 I/O 自动多线程化。

**深入追问：两个工具有依赖怎么办？**

> 当前没有 blockedBy 这样的依赖调度。依赖前一个结果的调用应放到下一轮，或者由程序明确安排。一个调用失败，也不会自动让后面的调用具有事务回滚语义。

**深入追问：为什么不并行修改？**

> 同文件修改可能冲突。要并行，应明确文件所有权，或使用独立工作区，再审核合并。

<a id="q09"></a>
### Q09：轮数、费用和上下文预算怎么控制？

**参考回答：**

> 执行器检查工具轮数和费用估计，本地请求还可以用 tokenizer 检查实际消息和工具定义的输入长度。一次模型响应可能有多个工具调用，所以十轮不等于十次工具函数执行。
>
> 提示词会提醒预算，但最终边界由程序控制。摘要和额外提醒也是模型请求，都应该纳入成本。

**深入追问：子 Agent 也受同一个预算限制吗？**

> 目前没有完整的父子共享预算账本，主要在子任务返回后汇总 Token，不能说已经实现严格全局额度控制。下一步应派发前预留预算、运行中记账，并为主 Agent 留出汇总和验收额度。

## 三、工具与技能体系（Tools / Skills）

代码入口：[tools.py](../../python/mini_claude/tools.py)、[mcp_client.py](../../python/mini_claude/mcp_client.py)、[skills.py](../../python/mini_claude/skills.py)。

<a id="q10"></a>
### Q10：工具怎样注册和分发？

**参考回答：**

> 工具定义表描述名称、用途和参数 Schema。模型返回工具名称和参数后，统一入口解析和检查，再交给对应处理器。内置工具调用本地函数，MCP 走外部服务路由，子 Agent 和 Skill 由 Agent 内部分发。
>
> 权限、日志和结果回传放在公共执行链里，新增工具就不必重复实现整套流程。

**深入追问：是不是完整 Tool Registry 或 Hooks 系统？**

> 当前更准确的描述是定义表与分发入口，有若干前后处理逻辑，不是完整插件生命周期或通用 Hooks 平台。

<a id="q11"></a>
### Q11：有 JSON Schema，为什么还需要校验？

**参考回答：**

> Schema 描述预期输入，但模型不一定完全遵守。运行时仍要检查 JSON 解析、必填字段、类型以及工具自己的操作条件。默认实现主要是解析和工具内检查，候选版补充了部分必填字符串检查，并不是完整通用 Schema 验证器。

**深入追问：参数错了要自动修吗？**

> 对有副作用的调用不能猜。应该说明没有执行、指出具体错误，附上仅供格式参考的示例，再由模型重新构造调用。

<a id="q12"></a>
### Q12：非法工具参数为什么会破坏后续对话？

**参考回答：**

> 一次非法调用被拒绝后，如果仍把非法 function arguments 原样放进后续消息，服务端可能连下一次请求都拒绝。
>
> 我的处理是保存原始审计记录，把已经有明确错误反馈的非法调用投影成可读证据，合法调用保持不变。程序不替模型修好参数并执行，也不猜缺失结果。

**深入追问：这会不会丢证据？**

> 发送表示和原始记录分开。模型收到可兼容的错误说明，本地保留原调用、解析错误和结果，方便追溯。

代码：[tool_protocol.py](../../python/mini_claude/tool_protocol.py)。

<a id="q13"></a>
### Q13：编辑前为什么一定要读文件？

**参考回答：**

> 读取后会记录文件路径和 mtime。编辑已有文件时，如果没读过，或文件在外部变化，就要求重新读取，减少基于过期内容覆盖文件的风险。替换还要求 old_string 唯一匹配。

**深入追问：这就能保证并发安全吗？**

> 不能。mtime 检查不是事务，检查和写入之间还有竞争窗口。多个写者仍需要文件归属、锁或独立工作区。

**深入追问：旧文本和新文本一样怎么办？**

> 后续候选明确返回匹配到了但未替换、文件没有修改，避免把无变化编辑误报成成功推进。这是候选改进，不应写成历史版本已经如此。

<a id="q14"></a>
### Q14：MCP 与普通函数调用有什么区别？

**参考回答：**

> 普通函数调用的能力和处理器直接在本地定义。MCP 提供外部工具的发现与调用协议；当前通过 stdio 启动服务进程，用 JSON-RPC 请求 ID 把响应对应到 Future，再返回 Agent。工具名加 server 命名空间避免冲突。

**深入追问：服务挂掉、卡住或输出过多怎么办？**

> 当前已有连接失败和关闭处理，但逐请求超时、断流后 pending 请求失败、stderr 持续排空和完整 wait 回收还需完善。我会先补这些资源与协议边界，而不是对有副作用的请求直接重试。

**回答边界：** 当前是轻量 stdio 实现，不声称支持完整 MCP 传输和生产连接管理。

<a id="q15"></a>
### Q15：Skills、system prompt 和子 Agent 有什么区别？

**参考回答：**

> system prompt 提供全局行为要求；Skill 是按需加载的某类任务方法；子 Agent 是独立上下文中的执行者。
>
> Skill 文件有元数据和正文，支持参数展开。普通模式把正文交给当前 Agent，fork 模式则创建子 Agent 执行。工具范围配置在 fork 创建时有实际过滤，普通 Skill 不等于自动重写主 Agent 的全部权限。

**深入追问：怎么维护技能版本？**

> 用户级和项目级技能有覆盖关系，还有进程内发现缓存。修改后应确认实际加载的版本，必要时重置缓存或重启；文档内容也不能自动升级成用户授权。

## 四、上下文治理

代码入口：[context_summary.py](../../python/mini_claude/context_summary.py)、[agent.py](../../python/mini_claude/agent.py)。

<a id="q16"></a>
### Q16：上下文压缩怎么分层？

**参考回答：**

> 先处理长工具结果：落盘并保留预览和路径；再整理较旧工具正文；需要时对旧历史生成结构化摘要，保留近期完整交互。发送前按实际模板计数，超限明确停止，不静默裁掉前面的消息。
>
> 历史默认大结果阈值是 30 KiB，后续候选改成 4 KiB。讲具体阈值时要说明版本。

**深入追问：只给路径，模型一定会再读取吗？**

> 不一定，所以需要检查模型是否能依据预览判断何时读取。落盘提供了回查能力，不等于模型实际利用了全部证据。

<a id="q17"></a>
### Q17：为什么摘要设计成六个字段？

**参考回答：**

> 六个字段是目标、约束、文件变化、测试、待办和关键事实。它们对应接续任务时最需要知道的内容。
>
> 文件变化区分尝试、已应用和已验证，测试区分计划、执行、成功、失败和未验证，避免把“准备做”误写成“已经做完”。

**深入追问：摘要还需要保留所有细节吗？**

> 不需要。摘要保存工作状态，近期交互保留操作细节，原始文件和日志提供回查依据。把全部细节重新复制进摘要就失去压缩意义。

<a id="q18"></a>
### Q18：怎么保证工具调用与结果不被拆开？

**参考回答：**

> 切分历史时检查调用 ID 和对应结果，只在完整交互边界切分。如果存在未解决调用、重复 ID 或孤立结果，就拒绝这次拆分，不强行压缩。
>
> 当前结构化摘要使用 keep_turns=2 的近期保留策略，不是另一项目的六步 Actor 历史。

**深入追问：为什么这是协议问题而不只是内容问题？**

> 因为 API 要求工具结果对应前面的调用。配对破坏后，模型无法理解来源，服务端也可能直接拒绝请求。

<a id="q19"></a>
### Q19：摘要通过格式校验，就能保证不丢重要信息吗？

**参考回答：**

> 不能。字段、类型和状态检查只保证结构，不保证事实。我们保留压缩前依据，校验失败时回退，关键状态仍通过实际文件和测试核实。
>
> 所以我会说降低信息丢失风险，并保留可追溯依据，而不是保证语义无损。

**深入追问：归档是不是永远保存了全量原始历史？**

> 压缩归档保存的是当时的消息状态。如果旧工具正文此前已经精简，不能把这份归档说成从未处理过的原始轨迹；还要结合执行日志和原始工具产物。

<a id="q20"></a>
### Q20：为什么压缩后 Token 反而变多？

**参考回答：**

> 总成本取决于单次输入长度，也取决于请求次数、历史重复发送、摘要开销和压缩后是否需要更多补读或修复。摘要没有省下足够历史，或者丢失信息引起反复尝试，都可能让总 Token 上升。
>
> 我们确实看到改版通过题增加但 Token 更高，也遇到过摘要请求本身超出窗口。下一步要单独给摘要请求做预算，而不是只调大窗口。

**深入追问：如何证明压缩有效？**

> 固定模型、任务和预算，同时比较关键事实保留、任务通过率、总 Token 和耗时，包含摘要自身成本。短任务很少触发摘要时，不能用它证明长历史收益。

## 五、Memory 与任务接续

代码入口：[memory.py](../../python/mini_claude/memory.py)、[session.py](../../python/mini_claude/session.py)、[execution_journal.py](../../python/mini_claude/execution_journal.py)。

<a id="q21"></a>
### Q21：Memory 放在哪里，怎么召回？

**参考回答：**

> 当前是按项目路径划分目录的 Markdown 记忆，分为用户、反馈、项目和参考资料。召回时扫描文件头，把候选清单交给模型选择，再读取相关正文。
>
> 预取通过 asyncio Task 异步进行，完成后注入上下文。它是文件加模型选择式召回，不是向量数据库，也没有 BM25 和 embedding 混合检索。

**深入追问：为什么没有直接上向量库？**

> 当前规模下文件方式便于检查和维护。我会先验证召回是否有实际收益；换存储不能直接解决记忆过期、来源不清和冲突覆盖。

<a id="q22"></a>
### Q22：Memory 怎么去重、合并和解决冲突？

**参考回答：**

> 当前主要按文件路径避免同一会话重复注入，保存时同名文件可能覆盖，并根据修改时间提示新旧。它没有完整语义去重、自动合并和冲突裁决。
>
> 如果完善，我会增加稳定 ID、来源、版本和适用范围。重复事实合并来源，矛盾事实保留冲突标记，明确被替代的内容记录版本关系，而不是静默覆盖。

**深入追问：同一路径更新后怎么办？**

> 仅按路径去重可能漏掉更新。建议结合内容哈希，并在会话恢复时恢复召回状态；这属于后续改进，当前不能声称已经完善。

<a id="q23"></a>
### Q23：Memory、历史摘要、会话快照有什么区别？

**参考回答：**

> 长期 Memory 保存跨任务可复用信息；历史摘要压缩当前任务的工作状态；会话快照保存当时的消息和使用量。执行日志则记录具体工具调用发生了什么。
>
> 临时待办不应无差别写入长期记忆，也不能只靠摘要判断某个有副作用操作是否已经执行。

**深入追问：为什么简历说可以接续任务？**

> 主要依据是快照和执行日志，不是因为模型记住了所有历史。更准确的说法是支持会话结束或中断后的加载接续，而不是已经实现完整跨会话任务调度。

<a id="q24"></a>
### Q24：原子会话保存怎么实现？为什么还要锁？

**参考回答：**

> 先在目标同目录写临时文件，flush 和 fsync 后用 os.replace 替换，再同步目录，避免暴露半写 JSON。锁则用于避免同一会话被两个进程同时推进。
>
> 原子替换解决半写问题，互斥解决多写者覆盖，两个机制不能互相替代。

**深入追问：Memory 文件也用同一套原子事务吗？**

> 目前没有。Memory 普通写入和索引重建不具备同等级保护，这也是后续需要补项目级锁和原子替换的地方。

<a id="q25"></a>
### Q25：文件改完，但完成日志没保存就崩溃，恢复怎么办？

**参考回答：**

> 执行前先保存快照和 started 记录，执行后再保存 completed。如果恢复时只有 started，操作可能已经发生，所以按结果未知处理，阻止自动重放，先核对实际文件或外部系统。
>
> 相同调用 ID 和参数已有 completed 时可以复用结果；同 ID 参数变化则报冲突。核验说明不会把原调用自动变成可安全重跑。

**深入追问：这是否保证 exactly-once？**

> 不能对任意外部副作用保证。我们提供完成结果复用和 unknown 阻断；更强保证需要外部系统的幂等键或事务支持。

<a id="q26"></a>
### Q26：重启后能恢复哪些东西，不能恢复哪些？

**参考回答：**

> 可以恢复消息、使用量、压缩事件和工具结果记录，并检查原模型和工作目录。不能通过 JSON 恢复已经结束的 Shell 进程、网络连接、MCP 服务内部状态或模型 KV cache。
>
> 当前也没有完整保存所有运行状态，例如长期调度、Memory 召回集合和跨重启轮数预算。因此这是任务上下文与执行记录恢复，不是整个进程 checkpoint。

**深入追问：有没有持久 TaskList？**

> 目前没有完整持久任务 DAG。摘要里有 pending，CLI 有 goal/loop，但不等于可重启的后台调度系统。若要建设，应单独保存任务状态、依赖和验收证据，再关联 session 和调用 ID。

<a id="multiagent"></a>
## 六、多 Agent 协作与维护

代码入口：[subagent.py](../../python/mini_claude/subagent.py)、[agent.py](../../python/mini_claude/agent.py)。详细维护方案见[技术手册第 10.1 节](INTERVIEW-TECHNICAL-GUIDE.zh-CN.md#multiagent-management)。

<a id="q27"></a>
### Q27：为什么选 Supervisor–Worker？

**参考回答：**

> 主 Agent 负责总目标、拆分和汇总，子 Agent 处理边界明确的探索、规划或执行任务。这能把大量检索过程留在子上下文，减少主上下文积累。
>
> 当前是委派后等待结果，不是完整平级团队、分布式工作流或自动依赖调度平台。

**深入追问：什么时候不该使用子 Agent？**

> 任务很短、必须传入大量父历史、或需要频繁交叉修改同一文件时，委派可能更慢。要看隔离上下文的收益是否超过额外调用和汇总成本。

<a id="q28"></a>
### Q28：子 Agent 是独立进程吗？隔离了什么？

**参考回答：**

> 当前不是独立进程，是同一 Python 进程中的不同 Agent 对象。消息历史、角色提示和工具集合独立，但共享文件系统和一些进程内资源。
>
> 它不会为每个角色加载一份模型权重，仍然调用外部模型服务。上下文隔离不能替代文件、网络和进程隔离。

**深入追问：两个 Agent 同时改一个文件怎么办？**

> 优先指定唯一写者，或者使用独立 worktree 后审核合并。mtime 校验只能减少过期修改，不能完整解决并发写入。

<a id="q29"></a>
### Q29：子 Agent 权限怎么继承？

**参考回答：**

> 当前 Explore 和 Plan 通过工具列表限制为读取、列文件和搜索；General 的工具更广。权限模式会保留父级 plan 和 auto，但其他模式可能映射为 bypass，所以不能声称所有父子权限都严格取交集。
>
> 改进方向是让子能力等于父授权、角色工具和任务范围的交集，并避免空工具列表退回全工具这样的边界。

**深入追问：提示词写“只读”够不够？**

> 不够。要看实际暴露和执行的工具，尤其是 Shell。严格隔离还需要操作系统级限制。

<a id="q30"></a>
### Q30：子 Agent 怎样维护生命周期、取消和清理？

**参考回答：**

> 当前有创建、运行、返回和 Agent.close，但委派入口没有统一 finally close，父子资源归属也不完整。
>
> 我会统一登记 parent session、父工具调用 ID、child session 和 task ID，记录客户端、后台 Task 和命令取消句柄。父任务取消时，取消并等待子任务收尾，再关闭它拥有的资源，避免全局取消误伤其他会话。

**深入追问：父进程崩溃，能直接新建子 Agent 重跑吗？**

> 不能。子任务可能已经修改文件或完成外部操作。恢复时先查父调用和关联子日志，已完成就复用，未知则核验。当前缺少完整父子关联管理，这属于待完善部分。

<a id="q31"></a>
### Q31：子 Agent 的预算和并发怎么管理？

**参考回答：**

> 当前主要在子任务返回后汇总 Token，没有完整全局预算账本。更可靠的方案是派发前分配或预留额度，调用过程中记账，取消、失败和摘要也计入，并为主任务留验收预算。
>
> 并发还要分模型请求容量、子任务数量和文件写入三个层次。Semaphore 只能限制数量，不能表达依赖或防止文件冲突。

**深入追问：提高并发是不是一定更快？**

> 不一定。服务端容量有限，更多请求可能只是排队；协作还会增加提示、汇总和验证成本。应该看实际吞吐和端到端耗时，而不是 Agent 数量。

<a id="q32"></a>
### Q32：如何相信子 Agent 的结果？

**参考回答：**

> 当前主要返回文本，主 Agent 不能把“完成了”当唯一证据。要核对文件 diff、实际测试结果和剩余问题。
>
> 若完善接口，我会要求返回结构化状态、文件变化、测试命令与结果、证据路径。returned 只表示拿到回复，verified 才表示经过验收。

**深入追问：不同子 Agent 结论矛盾怎么办？**

> 回到证据和适用范围，不按角色或多数票直接决定。优先核查当前文件和实际执行结果；无法核实的分歧明确标记，不合成一个看似确定的结论。

<a id="runtime"></a>
## 七、命令生命周期与故障诊断

代码入口：[command_runner.py](../../python/mini_claude/command_runner.py)、[tools.py](../../python/mini_claude/tools.py)。

<a id="q33"></a>
### Q33：为什么 Shell 同时涉及协程、线程和进程？

**参考回答：**

> Agent 用协程等待结果；阻塞运行器通过 asyncio.to_thread 放在线程池；真正命令通过 Popen 在外部进程运行。运行器用 selectors 交替读取 stdout 和 stderr，避免一个管道填满导致另一边卡住。
>
> 这三层分别负责组织等待、承载阻塞 I/O 和执行外部命令。

**深入追问：为什么不是直接 subprocess.run？**

> 一次性等待不方便及时显示输出、处理中途取消和控制日志大小。持续读取让我能保留超时前信息，并把取消与进程组清理结合起来。

<a id="q34"></a>
### Q34：取消 asyncio Task 为什么不够？

**参考回答：**

> 取消 await 不会自动停止工作线程，也不会杀掉外部 Shell。我们通过 Event 通知运行器，向进程组发送 TERM，宽限后 KILL，再等待清理完成后传播取消。
>
> 命令以新 session 启动，方便按进程组管理。主动创建新 session 逃离进程组的后代不在完整保证内，不能承诺任意命令都绝无残留。

**深入追问：日志能无限保留吗？**

> 不能。返回输出和磁盘日志分别有上限，并记录是否截断。清理和可观察性要有资源边界，不应为了保留日志耗尽磁盘。

<a id="q35"></a>
### Q35：长链路失败如何定位？

**参考回答：**

> 我按请求、模型输出、工具调用、工具结果、会话和独立验收分层看。先确认请求有没有发出、工具有没有执行，再看文件和测试，最后判断模型是否做出了错误决策。
>
> 会话 ID、工具调用 ID、参数和日志把这些证据关联起来。它支持任务级溯源，但没有覆盖模型内部状态或完整分布式服务追踪。

**深入追问：举个真实例子。**

> house 任务要求顶层函数，模型写成类方法。测试报导入错误后，它准确说出应该改成函数，却没有继续调用编辑工具。问题不是错误反馈缺失，而是模型描述修复后停止，循环又没有基于失败证据继续检查。

<a id="evaluation"></a>
## 八、评测、效果与改进方向

<a id="q36"></a>
### Q36：你怎么设计评测？

**参考回答：**

> 使用固定 60 道 Exercism Python 开发题，事先固定任务和难度分组，记录模型、提示词、工具和预算。Agent 在独立目录里运行，最后恢复原始测试做独立验收，不能让模型通过改测试自证成功。
>
> 两个 worker 共享常驻模型服务。评测关闭长期 Memory、MCP 和子 Agent，所以这些成绩不能证明全部扩展模块的收益。

**深入追问：这是不是无污染测试集？**

> 不是。题目公开且已经反复用于开发，无法排除预训练接触。我把它称为开发评测，并单独设计中断、取消和长历史测试。

代码：[评测说明](../../benchmarks/paired-v2/README.txt)、[worker](../../benchmarks/paired-v2/worker.py)。

<a id="q37"></a>
### Q37：实际效果怎么样，为什么有些优化反而退步？

**参考回答：**

> 历史同批原版 18/60、改版 24/60，但总 Token 从约 153.54 万增加到 181.96 万。后续增加提示、反馈和 Plan 的组合反而退步，不能简单认为功能越多效果越好。
>
> 最近失败接续的单变量对照从 10/60 到 13/60，没有丢失同批对照通过题，但 Token 增加约 7.6%。这是初步收益，不代表超过了历史 24/60，也不能宣称统计显著。

**深入追问：那 Plan 是不是没用？**

> 不能推广这个结论。只能说当前任务、模型、提示和预算下，该组合没有带来收益。相对历史还改过其他机制，只有更严格的消融才能分离原因。

<a id="q38"></a>
### Q38：为什么旧版重跑也会变分数？

**参考回答：**

> 固定 temperature 和 seed 并不自动保证跨运行环境的输出完全一致。服务端批处理、运行配置和模型执行路径都需要核对。具体波动来源还不能仅凭成绩认定。
>
> 因此我优先看同批配对、逐题差异和轨迹，保留历史结果；需要更强结论时再增加重复实验和稳定性检查。

**深入追问：三题提升能证明改动有效吗？**

> 它提供初步证据，但样本小、单次运行不够。我还要确认哪些题实际触发提醒、是否真的修复并复测，以及是否有成本或错误回归，不能只看总分。

<a id="q39"></a>
### Q39：下一步是继续提示词优化，还是做 SFT？

**参考回答：**

> 我会先修可确定的工程问题，再判断是否需要训练。比如工具结果是否真实、失败后是否继续执行、摘要请求是否超限，这些不能全部靠 SFT 修复。
>
> 如果在明确协议和稳定执行器下，仍持续出现同类指令遵循或工具选择问题，再考虑收集经过验收的轨迹做训练。训练前需要区分模型能力不足与环境、协议、预算错误。

**深入追问：近期具体怎么做？**

> 回到较强的旧提示词基准，单独测试失败接续；修复摘要请求预算；之后补子 Agent 资源关闭、权限和预算继承。不要同时更换提示词、Memory、规划和反馈，否则很难解释结果。

## 九、一分钟介绍与练习清单

### 一分钟介绍

> 我做的是一个轻量 Python Coding Agent，基于开源框架复现并二次开发。模型通过工具读取代码、修改文件和运行测试，执行器负责权限、预算、状态和结果反馈。
>
> 我主要补了三个方面：会话快照与执行日志恢复，Shell 增量输出、取消和进程组清理，以及结构化摘要和上下文回退。MCP、Skills、Memory 和子 Agent 主要是复用与集成。
>
> 我用固定 60 题开发评测区分模型停止和真正测试通过。历史改版取得 24/60，但 Token 也增加；后续实验还有退步，因此我会用单变量对照和轨迹分析定位问题，而不是只增加更多规则。

### 最优先练熟的五个问题

1. 文件已经修改，但完成日志没落盘就崩溃，为什么不能自动重跑？——[Q25](#q25)
2. 取消协程为什么不能结束线程和 Shell？——[Q34](#q34)
3. 摘要 JSON 合法，为什么仍可能不可信？——[Q19](#q19)
4. 模型已经读懂测试错误，为什么还是停止？——[Q06](#q06)
5. 子 Agent 独立上下文和独立进程有什么区别？——[Q28](#q28)

### 回答时始终区分的三个层次

| 层次 | 说法示例 |
|---|---|
| 已实现 | “当前代码按调用 ID 复用已完成结果。” |
| 已验证及范围 | “固定开发集的一次配对实验中，通过题数是这个结果。” |
| 改进方向 | “完整父子预算账本尚未实现，计划采用派发预留与运行记账。” |

### 简历表述可以收紧的地方

| 原表达 | 更准确的表达 |
|---|---|
| 跨会话加载接续 | 会话结束或中断后的加载接续 |
| 按读写权限划分角色 | 为探索、规划与执行角色配置不同工具集合 |
| 记忆去重、合并和冲突处理 | 当前已做路径级注入去重与时间提示；语义合并、冲突裁决属改进方向 |
| 完整多 Agent 管理 | 已有主 Agent 委派；生命周期、共享预算与资源归属仍需完善 |
| 压缩保证信息不丢失 | 降低信息丢失风险，保留恢复和回查依据 |
