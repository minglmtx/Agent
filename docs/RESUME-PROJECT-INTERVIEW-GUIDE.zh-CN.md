## 1. 简历原文与讲述边界

### 原文一：浏览器智能体与上下文

> 构建多网站浏览器智能体与上下文管理：实现覆盖电商、GitLab 等 5 类网站的 Browser Agent，统一 AX 观察、工具调用及错误反馈；实现 Token 预算与六步历史管理，并完成页面分块、历史语义摘要的方案设计。

解释顺序是“五站适配与执行协议 → 已实现的预算和近期历史 → 页面分块与语义摘要设计”。原文最后说的是**方案设计**，可以如实解释设计内容和没有启用的原因，不需要将其说成已经实现。

### 原文二：技能与SFT

> 搭建技能生成与 SFT 目标构造链路：搭建轨迹蒸馏、Skill 聚类去重与检索增强链路，结合 Qwen3-8B 生成候选策略；建设 Actor 执行、Teacher 修订及在线目标筛选流程，配套 Generator SFT 代码与目标构造流程。

解释重点是技能如何生成、验证并变成训练标签。这里的“在线目标筛选”是在实际环境执行后筛选目标，不代表每次执行都进行梯度更新，也不等于RL已经完成。

### 原文三：验证与修复

> 建立自动化验证与 AI 辅助修复机制：建立页面、数据库与产物联合判定及动作重放机制，定位并修复初始观察静默截断等框架问题；设计异常聚合、隔离复现、候选补丁和独立回归的 agent 辅助修复编排。

先讲已具备的取证、程序判定、诊断重放和编码Agent辅助开发，再讲后半句的编排设计。“AI辅助修复机制”落到已有工具与实践；“异常聚合到候选补丁的统一调度”目前应按设计介绍，不能说已部署无人值守自动修复平台。

### 逐项对应

| 简历中的点 | 可以展开的事实 | 需要限定的范围 |

| AI辅助修复 | 编码Agent辅助调查、修改与回归；统一编排有设计 | 不把设计角色讲成已部署的自主Agent集群 |

## 2. 项目开场：先把两条主线讲清

### 一分钟版本

> 这个项目面向五类网站的多步任务，有执行和技能学习两条主线。执行侧统一公开页面观察、动作协议和错误反馈，模型提出动作，程序负责执行和结果验证。技能侧把历史轨迹整理成可检索的Skill，再由Qwen3-8B生成任务策略，Actor执行，Teacher根据允许的反馈修订，最后筛选合格技能作为Generator的SFT目标。工程上重点处理上下文预算、任务初态、失败取证和资源收尾。已实现的执行与数据流程、具体实验验证范围、以及语义摘要和自动修复编排的设计，我会分别说明。

讲个人贡献时接一句本人能够举证的内容，例如：“我重点参与了初始观察交付、上下文预算校验和对应回归。”不要把文档覆盖的全部模块都归到个人独立完成。

### 三分钟顺序

1. 约30秒：为什么需要技能复用，以及为什么不能相信模型自报成功。
2. 约60秒：沿“观察→动作→执行→新观察→程序判定”讲执行链；沿“检索→生成→验证→修订→筛选”讲技能链。
3. 约60秒：讲一个实际参与且能定位代码的案例，推荐初始观察完整性或受控动作复现。
4. 约30秒：说明验证方法、完成范围和设计取舍。没有测量过的性能提升，不补百分比。

整体关系可手画成：

```text
历史轨迹 → 蒸馏/审查 → Skill bank → 检索 → Generator候选
                                              ↓
当前任务/公开初态 → Actor执行 → 证据判定 → 成功目标筛选 → 导出 → Generator SFT
                      ↑            ↓
                      └── Teacher修订 ──┘
```

这是算法与模块关系图，不表示每次普通任务执行都要调用Teacher或训练。

## 3. Browser Agent：统一哪些内容，保留哪些差异

### 可以直接讲的回答

> 五站共用任务执行生命周期与模型动作接口，网站适配器负责具体初始化、公开观察、取证和恢复。AX是可访问性树，给模型提供控件角色、名称、状态及当前节点标识，比让模型直接处理全部HTML更适合动作定位。模型输出经过协议解析和参数检查后才执行，错误再作为结构化反馈进入下一轮。

### 深入追问

**为什么不用固定CSS选择器或录制脚本？**

Actor需要面对不同任务与页面状态，不能只执行一条固定路径。适配层可以用程序接口完成基础设施与证据采集，但任务决策仍依据允许的公开观察。AX也不是天然完整答案，仍需检查页面就绪、观察范围和目标绑定。

**统一五站是不是所有网站写同一个判定器？**

统一输入输出和生命周期，不统一业务语义。查询、修改、导出需要不同完成条件。站点、任务族与合同版本要精确匹配，不能只凭网站名称套判定。

**模型生成不存在的工具或旧节点ID怎么办？**

执行前核工具名、参数结构和当前观察绑定。非法提议得到对应错误反馈，不绕过校验执行。当前版本有有限纠错及停止策略，具体阈值按选中配置说明，不把所有历史runner的阈值混为一个全局默认。

**这和普通网页自动化有什么区别？**

模型负责按目标选择动作，程序控制工具、预算和执行边界；任务成功由独立证据判断。与固定脚本相比决策更灵活，但引入模型不确定性，因此更需要轨迹、错误分类和可核验结果。

代码入口：[公共执行器][execute]、[Actor循环][actor-loop]、[历史动作协议][protocol]。公共执行器的代码存在，不等于每一站的实际部署均已完成验收。

## 4. 上下文管理：六步历史与语义摘要要分别讲

### 4.1 Token预算

> 预算针对最终发给模型的完整请求，包括系统提示、工具说明、任务、页面和历史。先按实际chat template和tokenizer计数，再考虑输出预留与额外开销。超限要明确拒绝或使用已选定的有界观察策略，不能静默丢掉页面后半部分。

可解释的预算形式：`可用输入 = min(配置输入上限, 总窗口 - 输出预留 - 未计开销)`。Actor现行目标是64K总窗口、输出4096；这是部署目标和配置要求，不是任意硬件、模型或历史请求都已通过64K验收。Generator与Teacher各按自己的配置处理。

**为什么不能直接按字符数估算？** tokenizer对中文、代码、标识符和重复结构的切分不同；最终模板还有额外token。精确计数应针对实际请求格式。

### 4.2 六步到底保存什么

旧`ActorProtocol`有默认六步历史窗口。增强的`ActorEventMemory`候选保存最近六次实际浏览器交互及对应公开观察、URL、返回/错误等；解析失败单列，不冒充浏览器动作。更早事件按策略选取并标明省略，完全相同页面可共享引用。

相关原文摘录策略按动作目标、附近/祖先上下文等选择历史页面内容，保留来源及省略标记。这是有损摘录，但不是让LLM自由改写事实。当前观察、历史页面及当前可用元素ID要分清，旧节点标识不能自动授权当前操作。

> 我们把提示词窗口、完整落盘轨迹和公开读取记忆分开管理。六步限制的是当前输入中的近期窗口，不意味着完整历史从存储中删除。

历史小规模验收核到两组使用真实模型与浏览器的合成UI控制，累计11次生成/动作；其中一组完成八步，验证了六步交互输入及较早事件保留。该回执明确默认启用为false，不是注册任务成功率或五站质量结果。原回执留在内部workspace，本发布分支不附原轨迹。

**为什么选择六步？** 这是已有实现与实验使用的窗口参数，不要讲成理论最优。若要比较窗口大小，应固定其他条件，测任务完成率、事实遗漏、输入token与运行成本；目前不编造该消融结果。

代码：[事件记忆][memory]、[历史原文摘录][quotes]、[动作协议][protocol]。

### 4.3 “完成历史语义摘要方案设计”怎么解释

可以这样回答：

> 简历这里说的是方案设计。我们考虑保留最近六步的原始交互，把更早历史摘要成已确认事实、完成的子目标、待处理变更、未解决错误和重要对象。摘要必须引用原事件，不能把“尝试保存”改成“已经保存成功”。当前实际采用的是更容易审计的结构化记忆和原文摘录，通用LLM摘要还没有作为已上线能力。

历史技术方案讨论过按旧历史长度或请求预算触发、使用本地模型生成受限摘要。这些属于历史设计初值，且自由摘要曾被移出当前实施待办；不要把它说成现行启用参数。也不要把Coding Agent项目中的会话摘要实现搬来证明本项目已做历史语义摘要。

**如果让你实现，会怎么做？** 以下是设计回答：

1. 只处理较早历史，保护当前任务、当前观察和近期交互。
2. 将事实、尝试、错误和未确认状态分开，附原事件引用。
3. 校验输出字段、对象引用和来源；无法验证的内容不标成已完成。
4. 保留原始轨迹；摘要失败用可容纳预算的原文/既有策略，仍超限则拒绝，不能无条件塞回完整历史。
5. 用长任务测关键事实遗漏、错误“完成”声明、成功率、累计token和摘要额外耗时。

摘要后文本更短不等于整体更快，额外模型调用也可能增加延迟。

### 4.4 页面分块怎么讲

> 近期历史短不代表当前页面短。长表格、代码、评论树可能单页就超预算，所以方案按结构保留行、段落和节点关系，并设计快照绑定、范围读取、覆盖状态及继续入口。读到部分内容必须明确不是全页，读取结果里的旧节点也不能绕过当前动作检查。

设计应保护表头与行身份、代码路径与行号、评论父子关系。单纯字符串切片会破坏这些关系。哪些网站和实际消费者已装配，需要按对应版本验收，不能用专项设计文档证明全部完成。

进一步阅读：[五站上下文方案](design/five-site-context-compression-v1.md)、[长输入与按需读取方案](design/five-site-long-input-handling-20261101.md)。

## 5. 技能生成：蒸馏、聚类与检索

> 历史轨迹包含大量具体页面和操作。蒸馏先把其中可迁移的经验整理成紧凑Skill，再做结构/质量检查和相似技能整理。检索根据当前任务找相关经验，Qwen3-8B结合任务和初始观察生成候选策略。

**Skill是什么？** 是带适用条件与完成判断的文字策略，不是可直接执行的工具函数，也不应固化旧页面的临时元素ID。

**“蒸馏”是不是训练了一个小模型？** 这里首先指从轨迹抽取、整理技能数据；后续SFT才更新Generator参数。不要把数据蒸馏和权重蒸馏混为一谈。

**如何聚类去重？** 现有代码使用归一化向量相似性与complete-linkage。合并时看跨簇最不相似成员对，避免仅靠相似链把两端不相近的技能串成一簇。`generator_sft.make_bank()`按网站分组，默认阈值0.92，选择簇内平均相似度较高的代表；通用SkillRecord整理也先选语义medoid，近似并列时再参考质量、证据等规则，不能把它说成只按质量选代表。

**去重会不会丢来源？** 聚类压缩经验表示，成员来源关系仍需保留，不能因为保留一个代表就抹掉其他来源，也不能把不同目标的任务都删掉。

**检索怎么防数据泄漏？** 先按数据split、来源与任务/目标排除等规则确定允许候选，再计算相似度。现有方法取top-6，但它是固定方法参数，不是已经证明最优的数值；检索不等于必须使用向量数据库或近似索引服务。

代码：[技能构建][skill-builder]、[后处理][postprocess]、[聚类][clustering]、[bank与SFT数据整理][generator-sft]。数据规模和实际bank版本要查对应原清单，不拿旧文档中的条目数当当前统计。

## 6. 目标构造与SFT：谁训练、谁只做推理

### 可以直接讲的回答

> Generator根据当前任务、初态和检索到的六条技能生成四个候选。Actor在满足初态要求的环境中验证候选，Teacher读取允许的轨迹与反馈进行修订，再交Actor验证。方法保留首轮Teacher和最多三轮修订规则。从成功尝试中按实际环境交互数选择目标，无成功则拒收。最后把原Generator输入和选中的技能JSON组成SFT样本。

这里描述的是方法与代码流程，正式来源是否有授权、输出是否合格、实际运行是否完成，需要分别判断。

**Teacher修改什么？** 修改技能策略，不修改网站判定标准，也不替Actor宣布成功。Teacher只能看到允许的证据与反馈，不能获得未授权的隐藏答案。

**在线目标筛选是不是RL？** 不是。这里通过真实执行筛选监督目标；SFT训练时优化目标技能token的交叉熵。Generator RL和Actor RL需要额外的rollout、奖励、参数更新和恢复接线。

**SFT训练谁？** 这条主线训练Generator生成技能的能力。prompt和padding位置label设为`-100`，只监督assistant目标；不能说这一步直接拿所有点击动作训练Actor。

**实际步数怎么算？** 按已记录的环境交互定义计数，和模型生成次数分开。解析失败不自动等于执行了一个浏览器动作；不要用聊天轮数替代该指标。

**为什么没有成功就不能训练？** 当前正目标构造流程需要已验证的正标签。有效失败仍保存，但不能改标签冒充成功。工程样本、合成夹具和原题正式训练目标有不同资格。

**训练效果怎么样？** 可说明实现了哪些代码、验证了哪些训练/恢复功能。已有小模型或合成数据验证不证明正式业务SFT效果；没有合法对照结果就不报成功率提升。公开代码中的训练接口也不等于当前生产训练已启动。

代码：[旧目标构造主线][stage1]、[正式来源验证][native-training]、[新构建编排][construct]、[SFT训练器][sft]。旧流程与新端口不能靠改标签互通，正式适配仍需原合同与验收。

<a id="verification"></a>
## 7. 自动验证：联合的是证据，不是模型意见

> 我们不以Actor的结束消息作为成功依据。任务合同确定完成条件，采集器获得相关证据，判定器检查条件，复核器再验证保存的事实与结果是否匹配。

| 任务语义 | 应检查的事实 | 单独不足以证明成功的信号 |
|---|---|---|
| 查看/导航 | 正确对象、页面内容与就绪状态 | 仅URL包含某个字符串 |
| 查询 | 答案及其独立可核依据 | 模型说“查到了” |
| 修改 | 正确对象的变更真正持久化 | 点击过保存按钮或出现提示 |
| 导出 | 文件存在、格式/内容及目标范围正确 | 下载按钮调用返回 |

“页面、数据库与产物联合判定”表示按任务需要结合多种证据，不要求每题都检查三类，也不是简单投票。

**页面提示成功但数据库不对怎么办？** 如果任务要求持久化且证据完整，未保存是业务失败；如果状态读取报错、取证缺失或对象不明，则是工程错误/未确认，不能直接用作训练负例。

**如何验证判定器自身？** 正控制证明正确结果被接受，负控制证明错误对象、未保存和缺产物被拒绝；恢复控制证明下一候选不会继承上一个候选结果。只检查一次正常样例不能证明所有边界正确。

**为什么要独立复核？** 防止执行过程或结果汇总遗漏信息。复核应读取原始证据并核合同，不是重复运行网站来替换原结果，也不一定再调用一个LLM评分。

**如何避免答案泄漏？** Actor/Generator只接允许的公开观察；私有参考、后台状态和隐藏判定材料保持在证据/判定侧。反馈经过合同限定，不因为Teacher更强就向它开放全部后台信息。

代码：[现场执行尾部][tail]、[独立复核][review]、[目标导出][export]；职责详见[技术手册](AI-APPLICATION-TECHNICAL-HANDBOOK.zh-CN.md)。

## 8. 动作重放：作为受控故障复现来讲

先区分两类“重放”：只读历史证据、重新计算判定；以及在隔离环境执行已记录动作。文件名含replay不必然表示再次操作浏览器。

内部已核的 `scripts/replay_admin_runtime_errors.py` 属于第二类。该诊断脚本未随本源码分支发布，下面说明的是所核内部实现范围，不声称公开仓库具有完整可运行的重放入口。

### 具体过程

1. 读取原任务与轨迹，建立隔离Admin现场。
2. 比较初始应用状态与原执行记录，不一致时拒绝把它当等价复现。
3. 按保存的动作顺序执行，不重新调用模型生成动作。
4. 节点ID变化时对照原观察和当前观察的元素描述，仅在目标唯一时映射；对特定动态ARIA标识存在诊断用规范化，歧义仍拒绝。
5. 保存映射、返回、错误与状态；脚本可以在首个目标错误或指定诊断位置停止，最后关闭资源。

> 重放的目的是减少模型随机性干扰，判断执行接口故障能否复现。它不算新的Actor成绩，不获得正式训练资格，也不保证任意动态网页逐字节重现。

**元素ID变了为什么不直接用旧ID？** 同一个数字可能指向不同对象。必须绑定当前观察，无法唯一匹配时停止，不能让复现脚本猜动作。

**时序不一样怎么办？** 有记录时可以选择复用原推理等待，但异步页面与外部服务仍会变化。记录复现条件和差异；未复现只能说明这次条件下没出现，不能宣布原故障不存在。

**这和“未知请求不重发”冲突吗？** 不冲突。受控诊断必须有自己的合法范围、隔离现场及证据归属；不能把它用于重试旧生产请求、真实支付或未确认副作用，更不能覆盖原失败记录。

## 9. 初始观察静默截断：能被代码支撑的案例

### 推荐讲述

> 我们关注过初始页面信息在交给Generator时是否完整。AX很长时，如果中间层按字符直接裁剪，末尾目标可能消失，后续看起来像模型不会操作，实际是输入交付不完整。对应实现把允许的公开初始观察完整序列化，并对最终消息使用实际模板和tokenizer计数；超限明确报错，不能悄悄删尾。同时用白名单排除私有答案字段。

这段讲的是问题机制与现有修复实现。若要讲“某次故障中我如何定位”，必须补上本人实际查到的原日志、修复前代码和回归回执；本次核查没有确认具体旧截断长度、最初作业和前后成功率，不应临场编造。

### 可以展示的实现细节

[generator_observation.py][initial-view]直接保留AX文本，序列化允许的公开字段；`require_context_fit()`调用tokenizer的chat template，对完整消息计数。超限抛错明确说明观察没有被截断。

内部旧回归 `tests/test_generator_observation.py` 包含：长AX末尾目标仍保留、私有字段不进入输入、缺失DOM状态不凭空补齐，以及预算刚好相等通过/超过预算拒绝。该旧测试未随本分支发布，不能把描述当成本次重跑结果。

**怎样判断是模型问题还是框架问题？** 对比原始公开观察、交付视图和实际发送消息，确认目标信息是否到达模型。若输入在程序层丢失，先修框架；若完整送达后模型选择错误，不能仅凭任务失败改框架。

**修了以后性能提升多少？** 完整性交付和预算边界可以直接验证；任务成功率提升需要固定版本、任务范围与对照实验。没有该证据时回答“验证了不丢目标与超限拒绝，尚不能给出整体成功率提升”。

**超过预算只是报错，会不会影响可用性？** 明确拒绝比静默删掉关键事实更容易诊断。进一步能力是确定性整理、合法窗口及按需读取，各自需要验证；不把扩大窗口或摘要当作无成本解决方案。

## 10. AI辅助修复：已有实践与编排设计分别回答

### 10.1 约一分钟回答

> 项目已经有轨迹和错误记录、判定细项、隔离诊断及回归检查，编码Agent可以辅助读日志、定位代码和提出补丁。我设计的进一步流程是先聚合异常、检查证据，隔离复现后再生成有限候选补丁，由独立检查验证。当前不能称为统一的无人值守自动修复服务；Agent建议不直接改变业务判定标准，也不自动取得发布权限。

这里的“设计”对应简历原文，不需要把尚未上线的编排包装成实际运行组件。

### 10.2 面试画图：以下是设计

```text
异常证据 → 分类/聚合 → 可复现性检查 → 隔离复现
                                      ↓
                           根因假设 → 有限候选补丁
                                      ↓
                         独立检查 → 合格候选 / 拒绝及原因
                                      ↓
                           原有发布与运行资格流程
```

图中每一格是责任，不要求一个独立模型或一个子Agent。已有工具尽量复用，普通模型业务失败不自动进入代码修复。

### 10.3 深入追问

**异常聚合怎么做？**

设计上保留每次失败的原证据，以失败模块、异常类型、相关版本和实际根因归组。相同错误文本可能来自不同原因，不能仅按字符串合并；不同文本也可能共享同一根因。聚合帮助选择共用修复，不覆盖原失败。

**Agent看什么输入？**

最小复现所需的任务合同、版本、允许的输入、完整异常链、相关代码和已有验收。按需读取，避免把全部历史塞入上下文；涉及私有数据要沿原权限提供，不把原日志随补丁公开上传。

**什么情况下不让它改代码？**

普通模型没完成任务、证据不足、环境不可用或请求结果未知，都不能直接当作代码缺陷。先分类、定位具体接口或不变量；无法复现则保留不确定性。

**怎么防止它把测试改松？**

原失败输入与验收标准独立保留。补丁在隔离源码候选中生成，检查原失败节点及实际受影响消费者。修改断言必须有需求/合同依据，不能以让测试变绿为理由；测试通过也不自动证明业务成功。

**独立回归是不是再找一个Agent同意？**

独立性来自固定输入、明确预期和重新运行实际消费者。模型审阅可以辅助，但不能取代程序测试、安装检查和必要真实证据。生成者与复核者角色分开，也不应共享任意修改验收标准的权限。

**为什么需要隔离两次？**

源码副本隔离避免覆盖已提交版本；网站数据库/浏览器实例隔离避免污染生产或让候选继承状态。只有隔离Git分支，不能解决环境污染。

**失败后自动重试几次？**

补丁候选数量与预算应有上限；历史草案曾讨论每问题最多两个候选，这是设计初值，不是已上线调度器默认。更重要的是区分补丁迭代与外部请求重发：未知副作用不能靠换ID重试。

**通过之后自动发布吗？**

不默认。先产生可审查的候选、差异和验收结果，再按既有授权、安装和消费者匹配流程切换。当前没有证据支撑“任意补丁自动上线”。

### 10.4 案例回答模板

按“现象 → 输入/版本证据 → 根因 → 最小修改 → 回归 → 剩余边界”讲述。可以选第9节的观察完整性，或第8节本人实际参与的动作复现。若只有设计，直接讲设计取舍，不补造某个修复Agent已经自动成功的故事。

## 11. 工程追问：角色管理、进程与状态

| 追问 | 可以展开的回答 |
|---|---|
| 多Agent怎么管理？ | Generator、Actor、Teacher有明确输入输出，程序状态机决定下一步；Evaluator/Reviewer不一定是LLM，模型意见不授予权限 |
| 四候选是不是四个并行Agent？ | 算法候选数与并发无关；实际并发受GPU、实例隔离、共享费用及原配置限制 |
| Agent失败如何接续？ | 区分未派发、派发未知、返回已存、待登记和已完成；保存结果优先补核，未知动作不重发 |
| 线程和进程在哪里用？ | 项目有进程会话/监督及部分有界并发实现；先说明具体路径，再谈用途，不能把每个角色都说成独立线程或进程 |
| 为什么超时还不够？ | 调用可能阻塞在原生库或I/O；需要取消、进程监督和有界清理，同时验证实际退出 |
| 进程结束是否代表恢复成功？ | 不代表。网站状态恢复、物理终止、请求/资源登记分别取证 |
| 为什么不无限保存历史？ | 提示词有预算；完整证据与模型当前输入分层管理，存储完整不要求每轮全量发送 |
| 为什么还要阶段断点？ | 在静态材料和完整结果处复用，减少昂贵重跑；活owner与会话留在同一生命周期，不把每个函数变成跨作业恢复门 |

执行顺序与并发边界可结合[技术手册的浏览器执行闭环](AI-APPLICATION-TECHNICAL-HANDBOOK.zh-CN.md#actor)理解；线程、锁、进程终止和原生接口细节按代码阅读指南定位实际实现。不要引入项目没有实现的技术栈。

## 12. 面试前的证据准备与最后复习

### 12.1 每项贡献准备四样东西

- 一句话说明自己实际负责的部分。
- 一个能打开的代码入口，能解释输入、输出及失败路径。
- 一项明确范围的测试或原回执，说明它证明了什么。
- 一个尚未证明的边界，以及为什么当时这样取舍。

对于“初始观察截断修复”，额外准备修复前后的真实差异和原失败记录。对于“六步记忆”，明确展示的是普通窗口还是增强事件记忆候选。对于“AI修复编排”，明确哪些环节由编码Agent辅助完成，哪些仍是设计。

### 12.2 数字怎么回答

| 数字 | 可用解释 |
|---|---|
| 五站、top-6、四候选、最多三轮修订 | 项目覆盖/方法参数，不等于最优性结论 |
| 六步窗口 | 实现与实验采用的窗口，不等于完整历史只存六步 |
| 64K/O4096 | 当前Actor部署目标；具体硬件与入口需精确资格 |
| 历史合成UI的11次调用/动作 | 有限兼容性验证，不是业务成功率样本 |
| 正式SFT收益、语义摘要收益、自动修复成功率 | 没有对应正式证据时不报数字 |

### 12.3 公开证据与内部核查的区别

本页代码链接指向发布快照，可据此阅读实现。语义摘要旧草案、Admin诊断脚本、六步记忆原实验及旧观察回归在内部workspace核查过，但不全部随本分支发布。本页不附任务内容、轨迹、数据库、模型响应、权限或费用账本。公开源码不足以复现对应现场时，应直接说明这个限制。
