# Goal：按交付推进，避免重复确认与验证

复制下面的提示词，并填写前三项即可使用。它不创建新运行权限，也不要求清空所有历史遗留项。

```text
目标：〔本次要交付的具体结果〕
当前入口：〔项目路径、当前交接/运行清单〕
完成标准：〔可检查的产物、必要测试或业务结果；沿用已有验收标准〕

请直接执行并推进到完成，不停留在方案建议。

工作方式：
1. 先核当前代码、有效回执与已有授权，列出最短必要路径；已有信息不重复问。
2. 只读当前任务需要的文档和模块。历史记录用于查证，不把所有旧规则和待办重新变成前置条件。
3. 在已有授权内直接完成可逆修改、只读调查及必要执行。不因换阶段重复询问“是否继续”；仅对阻塞信息或授权范围外的动作提问，同时推进独立工作。
4. 围绕一组相关改动合并实施和验证。只跑受影响路径、消费者及既定必要检查；未变且仍适用的证据直接复用。通过后立即推进，不追加同条件演示或重复验收。
5. 失败、证据冲突、停滞或依赖变化时才展开额外诊断。每次重试要有新证据、假设或修改；两次无进展就说明阻断并换有依据的方法，不能原样重跑。
6. 按实际资源和依赖批量处理就绪任务；同一可写实例保持顺序。等待期间推进独立工作，不循环轮询，不把一个分支的阻断扩展为整个项目停工。
7. 保留原始证据、train/dev/test 隔离、现有预算与必要收尾；不重放结果未知的副作用，不修改在途作业的冻结输入。需要新凭证时使用现有安全配置方式，不在日志中输出密钥。
8. 沿用一份任务清单，记录完成结果、证据、实际阻断和下一动作，不为每一步新增报告。测试/安装/模型/网站按项目要求在 Slurm 执行。
9. 达到完成标准后停止扩展，报告改了什么、如何验证、交付位置及实际限制。不得用测试通过替代业务成功，也不要继续问是否做无关优化。

遇到权限缺口，请一次说清具体动作、缺口及依据；已有授权不要重复索取。这个提示词不扩大既有费用或生产权限。
```

## 当前 SFT 主线：新版交付优先

以下整段可直接作为当前任务的 goal。它沿用上面的执行方式，不预设完成数量、API 状态或任何版本已经通过业务验收。

```text
目标：以做过架构优化的新版为后续主线，完成当前已授权首批训练目标构建和既定小规模 SFT。优先把业务链路接通，不继续扩大架构建设范围。

当前入口：读取当前工作区最新交接和原运行清单，确认新版与旧版各自的路径、版本和已有有效回执。核清新版距离首批交付尚缺的实际步骤，不重做全项目审查，也不把历史成功当成当前可用证明。

版本策略：
- 新版是主实现：保留已有模块划分、接口和阶段接续能力；冻结进一步架构扩建，只修当前交付实际阻断的缺陷、接线和必要适配。
- 不为了未来通用性新增抽象层、审批层或恢复平台。若当前交付确实需要改架构，应指出具体失败、最小改动和验证出口，在原授权内直接处理。
- 旧版保留为对照与必要时的临时交付路径，不同时扩建两套实现。
- 只有新版存在具体交付阻断，且旧版对同一任务与所需配置有仍适用的成功证据、满足当前执行条件时，才在既有授权内用旧版完成这批交付。记录选用依据，不仅因新版第一次失败就切换。
- 两版运行和产物分别标明代码、配置及来源；不得混用可写状态或无条件移植检查点。复用轨迹和产物需确认格式、语义与消费者兼容。

执行顺序：
1. 从当前已准备任务和最近有效阶段接续；需要时补候选生成与 Actor 执行，然后完成 Teacher 修订、Actor 复验、独立复核和导出。已完成且适用的阶段直接复用。
2. 在新版补齐明确缺口，合并验证改动路径和受影响消费者；必要检查及既有运行条件满足后直接提交首批，不再增加同条件演示。
3. 不等待所有网站、任务类型或 T1–T11 完成。已就绪成员按资源条件批量推进，同一可写实例保持顺序。
4. 有合格正式目标且既定训练条件满足后，完成小规模 SFT；不得用本地工程试跑或未复核目标替代正式目标。
5. 等待运行时推进独立的测试集工作。没有新证据不重复检查或提交；不新增 Summary Agent 或复杂压缩平台。

完成标准：交付首批合格目标及对应来源、执行和验证记录，按既定范围完成小规模训练并保存输出。若凭证、运行条件或合格目标缺失，如实记录具体阻断，继续完成独立可推进事项，不能标记正式闭环已完成。

执行纪律：沿用本文通用工作方式。已有授权不重复确认；保留费用与资源预算、数据隔离、原始证据和必要收尾；不重放未知副作用，不改在途冻结输入。达到交付标准后停止扩展，报告所用版本、实际结果、证据位置及剩余限制。
```
